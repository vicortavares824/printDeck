# Shared global cloud inventory with offline-first Flutter persistence

The backend `/api/supply` API moves from per-device partitioning to one shared global inventory: a fixed `device_id = "__shared__"` scope, a per-item non-destructive upsert on `/sync`, GET returning the whole shared set, and DELETE by `item_id` across the shared scope. The Flutter client becomes offline-first: a Hive box `supply_hub_items` is the local source of truth loaded on construction, every mutation persists locally before/independently of the network, push failures mark items pending instead of swallowing them, and `pullFromCloud` merges by `item_id` instead of overwriting. The device id is now persisted so the cloud no longer "forgets" items across restarts, and cold-start retry/timeouts were added for the hibernating Render free tier. The HTTP contract shape (paths, field names, `device_id` accepted) is preserved and no schema migration is introduced.

Watch for: a confirmed offline-delete resurrection gap — a delete whose cloud call fails is removed locally but reappears on the next pull because failed deletes are not tracked as pending (unlike failed upserts). Also note a sizeable bundle of unrelated translation/UI changes in the same set of commits.

**Verdict**: APPROVED

## High-level view

The backend scoping change is clean and matches the contract: `SHARED_SCOPE = "__shared__"` replaces `data.device_id` everywhere, the old `delete(...).where(device_id==...)` bulk wipe is gone, and `/sync` now selects-then-updates-or-inserts per item so an empty `items:[]` deletes nothing. GET and DELETE keep the `device_id` param for shape stability but ignore it for scoping. Schema untouched, `src/`, `alembic/`, and the sibling `backend/` project untouched, and the README documents both the shared-scope contract and the `app.main:app` vs `render.yaml` `src.main:app` start-command mismatch.

On the client, all Hive access is gated through a synchronous `_box()` helper that returns null unless the box is open, so the no-arg `InventoryNotifier()` the unit test constructs starts empty and every persistence call is a safe no-op under test — this is the detail that keeps the 7 existing tests green without touching the test file. Pending-sync tracking is a persisted id set under a reserved `__pending__` key; failed upserts land there and are retried on the next pull. The pull merge is non-destructive for created/edited items: it starts from cloud state and overlays any local item whose id is pending, so an offline-created item that never reached the cloud is never dropped.

The one real correctness gap is asymmetric: failed *deletes* are not tracked. `removeItemWithCloud` deletes locally and, on cloud failure, only records `_syncError`; the item is not added to any pending-delete set. The next `pullFromCloud` pulls it back from the cloud (it is in `cloudById` and not overlaid), so an offline delete silently reverts. This is narrow and sits at the edge of the stated acceptance criteria (which emphasize never dropping offline-*created* items), so it does not block, but it should be tracked.

<summary>Details</summary>

### Shared-scope rewrite on the backend

The three handlers now key off the module constant `SHARED_SCOPE = "__shared__"` instead of the request's `device_id`. `list_supply_items` selects `where device_id == SHARED_SCOPE` and `delete_supply_item` deletes `where item_id == ... and device_id == SHARED_SCOPE`; both keep the `device_id` query param in the signature purely for contract shape. The important change is `sync_supply_items`: the previous implementation ran `delete(CloudSupplyItem).where(device_id == data.device_id)` before re-inserting the payload, which made every sync a destructive full replace of that device's scope. That delete is removed. Each payload item is now looked up by `(SHARED_SCOPE, item_id)` and updated in place (title, description-or-`""`, quantity, is_bought, `updated_at = datetime.utcnow()`) or inserted fresh, with a single commit. An empty `items:[]` therefore touches nothing — the non-destructive guarantee the task demands. The smoke-test evidence in FEAT-001 (shared visibility across devices A/B, empty-sync retention, upsert-in-place, shared delete, 404 on missing) is consistent with this code, and `py_compile` of the router/model/schema passes here (exit 0).

### Client persistence gated so tests stay green

`InventoryNotifier` gains `boxName = 'supply_hub_items'` and `_loadFromHive()` called from the constructor. Every Hive touch goes through `Box<String>? _box()`, which returns null unless `Hive.isBoxOpen(boxName)`. This is the mechanism that lets the no-arg `InventoryNotifier()` in the unit test start empty and treat every `_persistItem`/`_deleteItem`/`_persistPending` call as a no-op, since Hive is never initialized under test. Confirmed by running the test: all 7 pass, and `flutter analyze lib/features/supply_hub` reports no issues. `app_setup.dart` opens the box in `openBoxes()` and removes it in `deleteBoxes()`, matching the existing box lifecycle.

### Pending-sync tracking replaces the silent catch

The old `_pushToCloud` swallowed failures in an empty catch under a comment that claimed data was "saved locally" though no local storage existed. Now `_pushToCloud(List<String> touchedIds)` persists the data first, and on failure adds `touchedIds` to the persisted `_pendingSync` set (stored as a JSON id list under the reserved `__pending__` key) and sets a non-blocking `_syncError`; nothing is rethrown to the UI. On success it clears the pending set and the error. `pendingCount` and `syncError` getters expose the state for the UI. The misleading comment is corrected to describe the box persistence and pending-retry behavior accurately.

### Non-destructive pull merge

```
pullFromCloud:
  cloudById   = { id -> item }  from api.pullItems()
  mergedById  = cloudById                      # cloud authoritative for synced ids
  for local item where id in _pendingSync:     # offline-created/edited win
      mergedById[id] = local item
  state = mergedById.values
  persist merged; re-push still-pending
```

`state = cloudItems` is gone. An offline-created item that never pushed is in `_pendingSync`, so it is overlaid onto the cloud result and survives the pull, then gets re-pushed. `_persistAll` rewrites the box to the merged list and prunes stale item keys while preserving `__pending__`. The rule is last-write-wins keyed on membership in the pending set.

### Offline-delete resurrection (the gap)

The merge protects created and edited items but not deletions. `removeItemWithCloud(id)` removes the item from state, removes `id` from `_pendingSync`, deletes it from the box, persists pending, then calls `api.deleteItem(id)`. If that cloud call throws, the catch only sets `_syncError` — there is no pending-delete record. On the next `pullFromCloud`, the item is still present in `cloudById`, is not in `_pendingSync`, so it is neither excluded nor overlaid; it comes back into state and is re-persisted locally. The same applies to the non-cloud `removeItem` path. The fix is symmetric to the upsert path: keep a persisted pending-delete set, replay the delete on next sync, and subtract those ids from the merge until the cloud confirms removal. Scoped narrowly this does not block the stated goal (which centers on not dropping offline-created items), but it is a real offline correctness bug.

### Device id persistence and cold-start retry

`SupplyApiService.deviceId` changes from a process-lifetime random value to one read from and written to the `settingsbox` Hive box under `supply_hub_device_id`, with an in-memory cache. This matters: with the shared scope the server ignores `device_id` for scoping, but a stable id still avoids churn and matches the documented contract. `pushItems`/`pullItems`/`deleteItem` are wrapped in `_withRetry`, which retries once on connection/receive/send-timeout or connection-error `DioException`s, and timeouts rose to 60s to tolerate the Render free-tier cold start. The same cold-start retry pattern was applied to `cloud_sync_button.dart` (telemetry), which is adjacent but outside the supply inventory feature.

### Pull-failure safety and test coverage

`supply_hub_page._syncFromCloud` still shows the red SnackBar on failure, and because `pullFromCloud` only reassigns `state` after a successful `api.pullItems()`, a network throw leaves local state and the box intact — offline reads keep working. Tests cover the in-memory domain rules (add/dedupe/increment/decrement/toggle/validation) and the empty-start guarantee. Not tested: load-on-construct from a populated box, write-on-mutation persistence, the pending-sync set surviving restart, and the pull merge itself (including the delete-resurrection path). These are the behaviors most likely to regress and have no automated coverage; the FEAT-002 spec listed Hive-temp-dir tests as optional and they were skipped.
