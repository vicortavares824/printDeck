# OWNERSHIP + ADMIN authorization for the shared cloud inventory

The shared `/api/supply` inventory gains per-item ownership and an admin override. Every row now carries an `owner_id` set server-side to the acting `device_id` on INSERT, so clients cannot forge it (`SupplyItemIn` has no `owner_id` field). `/sync` authorizes per item: an update to an item the device does not own is skipped and its `item_id` returned in a `forbidden` list under HTTP 200, so one unauthorized item never fails the whole batch. DELETE returns 403 for a non-owner/non-admin and 404 when the item is missing. Admin is a backend secret (`settings.ADMIN_CODE` from env; `""`/`"disabled"` disables it) presented via the `x-admin-code` header and confirmed through `POST /admin/verify`. The Flutter client stamps `ownerId` on create, gates mutations and UI controls behind `canModify`, handles the `forbidden` list and 403 non-blocking, and keeps the admin code in the local `settingsbox`.

Watch for: a confirmed null-owner authorization asymmetry — the client treats `ownerId == null` as "mine" (editable) while the backend treats `owner_id IS NULL` as admin-only, so edits to legacy null-owner items are optimistically applied locally then silently rejected into `forbidden`; this self-heals on the next pull but produces a transient local/cloud divergence and a confusing UX (controls enabled, edits silently dropped). Also confirmed: a pre-existing offline-delete resurrection gap now interacts with 403 deletes, and admin uses a non-constant-time string compare.

**Verdict**: APPROVED

## High-level view

Forgery is closed on the server side. `owner_id` is never read from the request body; it is assigned from `SupplySyncIn.device_id` on INSERT only, and admin is decided entirely by comparing the `x-admin-code` header against an env secret the client never sees. A client cannot claim ownership or admin by editing a payload — the worst it can do is assert ownership locally and have the backend reject it. This is the right trust model: the backend is the source of truth and the client rules are optimistic UI hints.

The null-owner rule is where client and server disagree, and the disagreement is safe but not clean. Client: `ownerId == null` means editable. Server: `owner_id IS NULL` means admin-only. For items this build creates the two never diverge (creation stamps the real `device_id` both locally and on the server), so the mismatch only bites legacy/pre-ownership rows: the user sees enabled controls, edits optimistically, the push lands the id in `forbidden`, and the next pull overwrites local with the authoritative cloud copy. No shared state is corrupted, but the local box briefly holds an edit the cloud rejected, and the user gets a generic "some items aren't yours" message with controls that looked editable.

The `forbidden` loop is handled correctly: rejected ids are removed from `_pendingSync`, so the client stops re-pushing them. There is one persistence edge — when removing the forbidden ids empties the pending set, the set is not re-persisted, so the stale ids survive a restart and trigger one extra harmless rejected push per session.

Offline delete of a non-owned item is blocked client-side: `removeItemWithCloud` and `removeItem` both run `_requireModifiable` first and throw `NotOwnerException`, and the card hides the delete control for non-owned items, so this is defense in depth. The carried-over offline-delete resurrection gap (a legitimate owner's delete that fails on the network reappears on the next pull) is unchanged by this diff and now shares a code path with the new 403 handling.

1. **Null-owner client/server mismatch** (confirmed) — client treats `ownerId == null` as editable, backend treats `owner_id IS NULL` as admin-only. Safe (self-heals on pull, no corruption) but produces enabled controls whose edits are silently rejected on legacy items. Align the client rule (treat `null` as not-modifiable unless admin) or backfill/migrate legacy `owner_id` so no null rows remain, and make the rejection message name the affected items.
2. **Pending set not persisted when forbidden empties it** (confirmed) — in `_pushToCloud`, `_pendingSync.removeAll(result.forbidden)` is followed by `if (_pendingSync.isNotEmpty) { clear(); persistPending(); }`; if the removeAll empties the set, `persistPending()` is skipped and the stale forbidden ids remain in the `__pending__` Hive key, causing one extra rejected push next session. Persist the pending set after the `removeAll`.
3. **Non-constant-time admin compare** (confirmed) — `is_admin` uses `x_admin_code == code`, a short-circuiting compare that leaks timing. Low risk given a network boundary and cold-start jitter, but use a constant-time comparison (`hmac.compare_digest`) for a secret.
4. **Admin code stored in plaintext in settingsbox** (confirmed, by design) — the verified code is persisted unencrypted in the Hive `settingsbox` so the header can be replayed. The trust model (device-local secret, backend is the real gate) is reasonable and documented, but the code is recoverable from device storage and never expires client-side; note this and consider a re-verify-on-launch or not persisting it at all.
5. **Offline-delete resurrection interacts with 403 path** (confirmed, carried over) — a legitimate owner's delete that fails on the network is applied locally and reappears on the next pull because failed deletes are not tracked as pending. The new 403 branch correctly surfaces a `ForbiddenException` but shares this untracked-delete path. Pre-existing from the prior pass; still worth tracking.
6. **No test for the forbidden-push or admin paths** (confirmed) — tests cover `canModify` and that non-owners cannot mutate locally, but not `PushResult.forbidden` handling (pending removal, no re-push), `verifyAdminCode`, or the null-owner optimistic-then-rejected flow. These are the new behaviors most likely to regress.

<summary>Details</summary>

### Ownership is server-assigned and unforgeable

`owner_id` is a nullable indexed column and is written in exactly one place: the INSERT branch of `/sync`, set to `acting_device_id = data.device_id`. The update branch never touches `owner_id`, and `SupplyItemIn` deliberately omits the field (the schema comment calls this out), so a crafted payload cannot set or change ownership. Admin is decided only in `is_admin` by comparing the `x-admin-code` header against `settings.ADMIN_CODE`, with `""`/`"disabled"` short-circuiting to `False` before any comparison. `/admin/verify` exists so the client can confirm a code before persisting it and returns `403` on mismatch without echoing the code. There is no path by which request data becomes authorization state — the forgery questions (a) are closed.

### The null-owner asymmetry

The two sides apply different rules to a null owner:

```
client canModify(item):            backend _can_modify(item, dev, admin):
  if isAdmin: return true            if admin: return true
  if ownerId == null: return true    if item.owner_id is None: return false
  return ownerId == deviceId         return item.owner_id == dev
```

For items created by this build the branch is never exercised with `null`: `addItem` stamps `ownerId: _deviceId` and the server stamps `owner_id = device_id`, so a freshly created item is owned on both sides. The divergence only reaches legacy rows (created before ownership, `owner_id` NULL in the DB). There the client enables the controls and lets the user edit; the push updates local state and Hive, the server refuses the update and returns the id in `forbidden`, the client drops it from pending and shows a count-only message, and the subsequent `pullFromCloud` — where the id is no longer pending — overwrites the local copy with the authoritative cloud row. The net effect is a transient divergence that resolves on the next pull, not a corruption of shared state, which answers (b): the mismatch is safe. It is not clean: the controls looked editable, the edit vanished, and the message does not say which item. Aligning the client (`null` → not modifiable unless admin) or backfilling `owner_id` removes the asymmetry; today's safety depends on the pull always following and winning.

### Forbidden handling stops the re-push, with one persistence gap

`pushItems` parses `{synced, forbidden}` defensively (falls back to `items.length`/empty when the shape is unexpected) and returns a `PushResult`. `_pushToCloud` removes the forbidden ids from `_pendingSync`, so they are not retried — answering (c): there is no infinite re-push. The gap is the persistence ordering:

```dart
if (result.forbidden.isNotEmpty) {
  _pendingSync.removeAll(result.forbidden);
  _syncError = 'Alguns itens nao sao seus ...: ${result.forbidden.length}.';
} else { _syncError = null; }
if (_pendingSync.isNotEmpty) { _pendingSync.clear(); await _persistPending(); }
```

When `removeAll` leaves the set empty, the `isNotEmpty` guard skips `_persistPending()`, so the on-disk `__pending__` key still lists the forbidden ids. On the next launch they reload as pending and get pushed once more, rejected again, and dropped again — harmless but an avoidable round trip. Persisting after the `removeAll` (or unconditionally) closes it.

### Admin trust model and the stored code

`verifyAdminCode` posts the candidate code in a one-off `x-admin-code` header; on 200 it calls `setAdminCode(code)`, which writes it to the `settingsbox` Hive box, and thereafter `_headers()` attaches it to every `/sync` and DELETE. `isAdmin`/`adminCode` read straight from that box. This is a sensible client model — the code is only a key to replay the header, and the backend re-validates on every request, so a stolen/forged client value is worthless without the real secret. Two notes for (d): the code sits unencrypted in device storage and is recoverable by anything that can read the box, and there is no client-side expiry or re-verification, so a device stays "admin" until an explicit logout even if the server secret later rotates (the server would then reject it, landing edits in `forbidden` or DELETEs in 403 — fail-closed, which is the right direction). The non-constant-time `==` in `is_admin` is a minor timing leak on a secret; `hmac.compare_digest` is the cheap fix.

### Offline delete of a non-owned item is blocked, but owner deletes can still resurrect

Both delete paths call `_requireModifiable(id)`, which throws `NotOwnerException` when `canModify` is false, before any state change — so an offline attempt to delete someone else's item cannot even mutate local state, and the card hides the delete button for non-owned items regardless. That answers (e): offline delete of a non-owned item is refused locally and never queued. The 403 branch in `deleteItem` translates the backend refusal into a `ForbiddenException` that the card catches and shows non-blocking. Separately, and unchanged by this diff, a legitimate owner's delete whose cloud call fails is applied locally but not tracked as a pending delete, so the next `pullFromCloud` pulls the row back (it is in `cloudById` and not overlaid by pending). That resurrection gap was raised in the prior pass and still stands; the new 403 handling shares the same untracked-delete path.

### UI gating and reactivity

The card gates the delete button, the quantity +/- and the bought/again toggle, and the read-only hint on `canModify(item)`. `loginAsAdmin`/`logoutAdmin` reassign `state = [...state]`, so the provider rebuilds and the cards re-evaluate `canModify` after an admin transition. One reactivity seam: the page reads `isAdmin` via `ref.read(...notifier).isAdmin` in `build` rather than watching it, so it refreshes only because the surrounding list state changes on login/logout — an implicit dependency that works today only because both admin paths bump `state`.

### Cosmetic: UTF-8 BOM added to touched files

Every touched Python and Dart file now starts with a UTF-8 BOM (`\ufeff`) on line 1 (`´╗┐from ...`). The backend smoke test passing shows Python tolerates it, but a BOM on `.py`/`.dart` sources is unintended, can confuse some tooling, and bloats the diff. Strip it from the changed files.
